| D-123 | Policy: the setup CLI actor is trusted for every action; `api_key` and `system` actors are denied every app action; unknown actions are denied; in `own_only` mode only the super admin can reassign a deactivated member's donors | Least privilege; the CLI is the break-glass path (D-103); API keys only reach `/api/v1` | CIC wants members to claim orphaned donors in `own_only` mode |
| D-124 | Frontend uses TypeScript 5.9.3, not 6.x | `openapi-typescript` 7.13 (approved, generates the API types) declares a `typescript ^5` peer dependency; forcing it onto 6.x risks silent codegen breakage | `openapi-typescript` supports TypeScript 6 |
| D-125 | Benevity `Match Amount` becomes a second gift (`is_matching_gift`, payer = company) credited to the same donor as the donation; `row_key` for it is the Transaction ID plus `:match`; fees (`Cause Support Fee` + `Merchant Fee`) reduce the donation's net | The documented report carries the match beside the donation; the match is real revenue and the relationship belongs to the employee, but reports must be able to separate employer money | CIC wants matches credited to the company instead |
| D-126 | The donor API (list, detail, timeline, create, edit, contacts, next steps) is built by lane C in Phase 2, not lane A; ownership changes and reminders stay with lane A in `routes/app_ownership.py` | PLAN gave lane B donor screens but no lane the donor endpoints, and acceptance test 7 needs them; lane A already carries the whole import pipeline | Lane A finishes early |
| D-127 | CIC decision: supersedes the employee-credit portion of D-125. Credit employees only for their own donations. Import employer matches as separate gifts with `is_matching_gift = true`, company payer and source transaction ID suffixed `:match` before row-key hashing; retain donor linkage for traceability, but exclude matches from donor totals, lifetime giving, retention and all amounts pre-filled in donor messages. Matches remain org revenue. Preview class counts are physical source rows, with separate gift counts, donation cents and match cents; reconcile both rows and total cents. | CIC distinguishes employee giving from employer revenue. Board members use donation-only dashboard/reminder data and edit message amounts by hand; a Benevity row can generate two gifts without becoming two source rows. | CIC explicitly changes donor-credit policy |
| D-128 | The public API rate limit (60 requests per minute per key) is counted in memory per process | Render runs one uvicorn worker, so it is exact in production; no new table or migration this phase, and counting in `audit_log` would fill it with read calls | The app runs more than one worker, or restarts must not reset the count |
| D-129 | A donor's free-text `notes` follow the contact-detail rule (owner and active super admin only), same as email and phone | Notes often hold personal details; gift history and timeline stay open to every member (D-104) | CIC wants notes shared across members |
| D-130 | Spreadsheet changes to matched existing donors require explicit uploader approval per field. Preview exposes proposed values, hides old values without DON-3 contact access, and counts update rows separately. Commit changes only approved name, organization, email, phone or notes fields, preserves ownership and audits once per donor in the import transaction. Omitted columns preserve values; approved empty cells clear them. Never learn rejected spreadsheet contact aliases. | CIC requested confirmed donor updates for Phase 3 (#105); silent overwrites would undermine uploader consent. | CIC changes its spreadsheet update policy |
| D-131 | CIC decision: when a donor chose to be anonymous, their gift is never attached to a donor record. In this data that means any Benevity gift with `attribution = anonymous` (Benevity hides name and email only when the donor opts out). `POST /gifts/{id}/attribute` refuses these with 409 ("This donor chose to stay anonymous; the gift stays unattributed."); anonymous gifts from other sources stay attributable. The gifts still count in org revenue and reports, unchanged. | A donor's opt-out must hold even if a board member later guesses who gave. Other sources have no opt-out signal, so an anonymous row there only means the details were missing | CIC reverses the decision, or another source gains an explicit anonymity flag |
| D-132 | Manual and bulk reassignment set the new owner's `last_assigned_at`, like round-robin does | CIC lead asked for it; hand-offs count as assignments for the tie-break, so a member who just received donors waits longer for the next new one | Round-robin balance looks unfair after bulk moves |
| D-133 | A message's approval covers a SHA-256 of subject and body together, stored when a person approves; any edit voids it, and send re-checks it | MSG-4 says the body hash; the subject is also read by the donor, and an edit that skipped the subject would send unapproved words | Never |
| D-134 | Default message templates live in code (`services/messaging/defaults.py`) and are stored on first use; text in `[EDIT: ...]` must be replaced before approval | Nothing is seeded and there are no migrations; a person should write the personal part of a quarterly update | CIC wants editable defaults in the database from day one |
| D-135 | Full-access keys act as their creating member with full permissions except governance (flatten, scope, super admin) and key management; `/api/app` is not yet a versioned public contract | CIC wants outside apps to read and change data without a browser login. Acting as the creator keeps one permission model and puts the creator's name on every audited change; refusing governance and key minting stops a leaked key from escalating or outliving its revocation | `/api/app` gets a versioned public contract, or CIC wants keys with narrower scopes |
| D-136 | Arbitrary import layouts are handled by AI-assisted column mapping, specified and built separately; the Zeffy contacts sample is kept only as a reference layout | CIC: files can have any columns. A per-format adapter for one sample would not generalize |
| D-137 | An optional board member column sets the owner of new donors and proposes owner changes for existing ones (uploader approves); unmatched names fall back to round-robin | CIC listed "contact person (board member)" as a field; matching by email then exact name avoids guessing |
| D-138 | Scheduled jobs run as `python -m app.cli run-job <job>` from a Render cron job, are off by default, write `job_runs`, and never send if the setting is off | Keeps one codebase, no new service; CIC asked for quarterly board emails; off by default keeps the demo and the brief's human-send rule safe |
| D-139 | Automated thank-you emails are a setting (`auto_thank_you`), off by default, audited when changed | CIC asked for automation; the brief says a human sends every outbound message. The setting lets CIC choose after the organizers answer |
| D-140 | Stay on one Render service; Vercel frontend is roadmap | CIC prefers Vercel for html/css/js; our React build is html/css/js. Splitting today adds cross-site cookie and CSRF risk hours before the freeze |
| D-141 | Dynamic fields cover donors and gifts; built-ins can be relabeled, reordered and hidden but not deleted or retyped; removing a custom field deactivates it and keeps values; `/api/v1` and MCP never return custom values | "Add, edit, remove fields" without losing data or breaking imports, dedupe and reports that depend on built-in fields |
| D-142 | Brand: CIC Dark Green `#007A3D` is the working color, CIC Green `#00A850` accent only, per CIC brand guidelines (Nov 15) | `docs/BRAND.md`; contrast checked against NFR-4 |
| D-143 | Custom roles are permission sets over org-wide actions plus two donor-wide grants; ownership rules, DON-3 and governance stay in `policy.py`; the built-in Board member role reproduces today's matrix | CIC wants roles and permissions customizable. Letting roles override ownership or governance would reopen every security test hours before judging; this keeps the policy matrix as the regression check |
| D-144 | Super admin can be created in the app by nomination plus a second member's confirmation, and removed only by the super admin, which returns the org to flat (replaces the CLI-only GOV-2 and no-delete GOV-3) | CIC wants the hierarchy changeable in the app. Two people are required so no single member can seize admin control; the setup command remains the break-glass path |
| D-145 | Assistant proposes, human confirms; speech-to-text in the browser, no audio stored; donor list never sent to the LLM. Three tools only (log contact, follow-up, thank-you) from one registry; off unless `assistant_enabled`. Refines D-118 (behind a flag, human approves) | A sentence like "called Maria, remind me Friday" saves minutes for volunteers on phones; names are matched on our server among donors the member owns, so the model sees only the sentence and the date, and every write still goes through the existing endpoints, policy and audit |
| D-146 | Fields are deactivated, not deleted; built-in fields can only be relabeled, reordered or hidden (never deleted, retyped or re-keyed); a field's `is_contact` flag follows DON-3, so its values show only to the owner, the active super admin or a full-access key | Removing a field must never lose data, imports and dedupe depend on built-ins, and a custom field could otherwise leak phone or email to every member (D-104) |
